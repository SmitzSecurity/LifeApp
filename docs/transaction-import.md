# Transaction capture and reviewed imports

September 16, 2026. Budget has a persistent bottom-right + that opens Log transactions. It replaces the inline Quick transaction form. Category allowances sits at the top left and Expected income & expenses at the top right on desktop; mobile stacks them in that order. Transaction history follows the other budget sections. The existing manual transaction editor, version checks, planned-payment behavior and exact save retries remain available inside the new window.

The camera action opens the device's image capture picker where supported. The paperclip accepts the existing bounded receipt images, PDFs, text/CSV/TSV/JSON, XLSX and DOCX. Choosing a file prepares it locally. Only an explicit Extract with AI submits source content and account-owned category names to Google Gemini. No journals, unrelated goals or financial balances are added to transaction categorization context. Files are not stored as binaries; the existing source text and attachment fingerprints support saved drafts and exact retries.

Extraction uses `intent: transactions` in the existing `budget:` builder namespace, shared usage ledger, attempt/cost limits, admission checks, attachment validation and token preflight. It has a separate strict transaction result schema and JSON instruction. Budget and Loan draft formats remain unchanged. Unknown provider/storage outcomes retain their reservations; status reconciliation is read-only, bounded and never automatically replays generation. Closing the window can dismiss waiting while an already submitted result finishes in Saved drafts.

Each draft contains up to 50 transaction rows with stable server-assigned IDs. Missing dates or amounts stay blank for review. A receipt produces its paid total rather than both items and a total. Statement instructions exclude balances, summaries and pending rows; card payments are transfers. Unsupported currencies and refunds/reversals are identified for separate review rather than fabricated as income or converted. Source text, category names and attachments are data, never instructions.

Category suggestions must match an active saved category for that exact transaction month; unknown suggestions stay blank. Users can edit the amount, date, description, type and category, deselect rows, or explicitly add a category and allowance. Likely matches to recorded transactions and repeated draft rows start unchecked. These are review hints, not proof of identity. Selected expenses require valid categories and actual dates through today. Historical transactions can span months. A missing month starts with category definitions and zero allowances, empty goals and no recurring items; importing history must not fabricate old bills or schedules.

Saving submits one frozen reviewed batch to the bounded `?transaction-import` endpoint. Category additions, any required historical budgets, all selected transactions and a minimal import receipt are one guarded atomic write. Concurrent unrelated budget changes are preserved; changes to a selected category require renewed review. Rows retain their draft IDs. A lost acknowledgement retries the same batch and returns the saved result without duplicating transactions. Reopening an adopted source cannot recreate deleted or purged transactions. Ordinary resource writes cannot create or alter import receipts.

The internal `transaction-import` receipt keeps IDs and hashes, not receipt images or transaction descriptions. It remains after individual transaction deletion to prevent replay; account deletion removes it with other resources. Export validation includes receipts and the new AI snapshot/result shape. No migration, runtime flag, cap, consent, Cron or production change is required. After use, do not roll back to code that rejects transaction build intents or import receipts.

The prelaunch review adds Delete to completed or failed transaction drafts in Saved drafts. It uses the existing `budget:` build visibility action and seven-day Trash; restoring the draft preserves its source, extracted rows and accounting. Deleting a draft does not delete transactions already adopted from it. Generating or uncertain jobs do not expose this action. An unconfirmed deletion retains its exact build identity, a reachable Retry delete action and navigation/write locks; it never replays extraction or releases usage holds. A later authentication rejection cannot settle a previously unconfirmed extraction, import or deletion, so those exact retry snapshots remain available after a subsequent 401/403 response.

Settings also uses a scrolling form above a persistent Cancel/Save footer. Automation & email stays with the fields. The former inline Settings saved label and save-success banner are removed; errors and existing settings save/cancel behavior remain.
