# Offline saves and reconnect sync

The signed-in browser now keeps bounded copies of previously opened LifeApp data in account-specific IndexedDB storage. Journal responses and ordinary workout, routine, cardio, written workout note, budget resource and manual transaction saves can be saved locally, including consecutive workout sets. A global status distinguishes saves on this device from confirmed cloud saves. Reopening offline uses the last authenticated app shell and cached assets after an initial online visit has prepared them.

Local save acknowledgements are returned only after IndexedDB commits. Every queued request keeps its exact serialized body, original mutation or resource ID and expected version. Saves replay sequentially while LifeApp is open, on reconnect, when returning to the foreground and on a bounded 30-second retry. The browser uses a cross-tab lock so two tabs cannot replay or rewrite the same queue concurrently. The server checks the expected opaque account on every request; a separate read-only identity probe cannot authorize a write for another account.

Unknown network/server outcomes remain queued and retain their exact payload. Another device's version conflict, validation rejection or expired session pauses replay. No automatic rebase or overwrite occurs. The review dialog preserves local changes, allows a private JSON download and offers an explicit whole-queue discard/reload after a definite conflict or rejection. Authentication/payment pauses retain their queue for exact retry after the user resolves access. Sign-out blocks while any device-local saves need review/sync. Confirmed sign-out and account deletion clear local account data and shell caches, coordinate with in-flight locks and notify other tabs.

This is foreground reconnect synchronization, not an operating-system background upload service. Keep the browser's site data until sync finishes. Private browsing, disabled IndexedDB/Web Locks, browser eviction or manually clearing site data can prevent offline persistence. The app reports unavailable local storage rather than claiming a successful save. Reads have a 2 MB per-result and 8 MB aggregate bound; queued writes have an 8 MB / 500-save bound and are never evicted to make room.

AI/provider calls, Settings/profile changes, consents, deletion/Restore/Trash, reviewed multi-month imports and category/recurring-item editors require a connection and confirmed preceding saves. They never enter automatic replay. Previously unvisited data cannot be invented offline; new reads outside the cache request reconnection. No cap, consent, migration or deployment flag changes are included. This release excludes the separate subscription implementation.

The installable web manifest provides standalone home-screen support. The service worker only caches same-origin app assets and the authenticated HTML shell; it does not cache API responses, authentication routes or provider requests. The private shell is invalidated on a sign-in redirect or confirmed account clearing. Asset precaching follows a bounded same-origin import graph and the resources actually loaded during first startup. Workout notification clicks focus the app and request its guarded workout navigation.

Synthetic tests cover durable serialized reloads, dependent revision ordering, exact retries after dropped acknowledgements, account mismatch isolation, explicit conflicts, disallowed replay actions, skipped-set preservation and bounded cached reads. A browser fixture with a real transport disconnect verified an offline set save, app reload from the cached shell, a second set and rest change, then ordered reconnect sync with unchanged workout identity and no duplicate sets. Physical iOS/Android suspension, eviction and offline-reload behavior still need device verification.
